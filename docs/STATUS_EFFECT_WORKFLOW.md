# 状态显示与新效果开发工作流

本文约定角色属性、战斗状态和新卡牌效果从领域模型到 Web 界面的完整开发流程。
目标是让服务端始终负责结算，让前端稳定、清楚地解释状态，同时避免把内部队列或
对手私有信息误发给浏览器。

## 界面信息层级

牌桌状态区参考《杀戮尖塔》的阅读顺序，不把所有数字做成同等权重：

1. **核心生存资源**：生命始终显示为 `当前值/最大值` 和进度条；低于 50% 变为
   警戒色，低于 25% 进入危急提示。
2. **核心行动资源**：能量使用独立核心组件和大号数字，不能混在普通属性列表中。
3. **次级战斗属性**：防御、力量、中毒以紧凑属性块显示；中毒为零时隐藏。
4. **角色专属资源**：形态、业力、饱食度、敏捷、动能、献祭和心连心放在可换行
   的资源标签区，零值仍可显示，以便玩家知道该机制存在。
5. **临时效果与实体**：免疫、致盲、插入物、生物等使用独立效果或实体组件，
   不塞入角色专属资源行。

所有需要解释的项目必须可悬停，并支持键盘 `Tab` 聚焦与 `Esc` 收起。生命条还必须
暴露 `role="meter"`、当前值和上下限，不能只依赖颜色传达信息。

## 状态的归属与可见性

状态只有一个权威来源：Python 服务端。React 只根据状态视图渲染，不能自行计算
伤害、资源消耗、层数或持续时间。

| 数据类型 | 放置位置 | 示例 | 默认可见性 |
| --- | --- | --- | --- |
| 所有角色共有的核心值 | `CharacterState` | `health`、`max_health`、`energy`、`strength`、`poison` | 双方公开 |
| 所有角色都可能受到的效果 | `CombatStatuses` | 免疫、致盲、插入物、生物威胁 | 按字段审查 |
| 角色独有资源 | 角色包的类型化 dataclass | `WarriorData.heartlink_layers`、`SlugcatData.karma` | 通常双方公开 |
| 牌区和选择过程 | 房间/选择状态 | 手牌、待加入手牌、待选择索引 | 仅拥有者或服务端内部 |

`_public_player_payload` 是 Web 公开投影的安全边界。新增字段不能因为“前端需要”就
直接暴露；必须先决定它属于 `public`、`owner_only` 还是 `internal`。尤其是
`pending_*`、随机池、待选项和对手手牌等字段应留在拥有者视图或完全不发送。

## 新增属性或效果的标准流程

### 1. 先写规则和稳定标识

- 使用稳定的 `snake_case` 标识，例如 `bleeding`，不要让中文显示名充当协议键。
- 写清楚叠层方式、上限、触发阶段、递减/清除时机、目标、是否公开以及零值是否展示。
- 区分“资源”“增益”“减益”“规则标记”和“内部队列”；这会决定状态归属和 UI。

### 2. 放入正确的领域模型

- 通用效果加入 `card_duel/core/models.py` 的 `CombatStatuses`。
- 角色专属资源加入对应角色包的 `state.py` dataclass。
- 只有所有角色都必然拥有的核心战斗值才加入 `CharacterState`。
- 设置明确默认值，并在角色 `lifecycle.py` 的 `initialize()` 中建立角色初始值。

不要新增无结构的 `dict`，也不要把角色编号判断写入 `core`。效果逻辑仍通过角色目录、
`CardPlayContext`、回合阶段处理器和 `CombatEngine` 组合。

### 3. 实现权威结算

- 在角色 `effects.py` 或通用规则中改变状态；UI 事件只发送动作意图。
- 持续效果注册到明确的回合阶段，并用优先级固定多个效果的顺序。
- 生命损失继续经过 `CombatEngine`，不要绕过防御、免疫和角色死亡能力。
- 所有选择型效果保持事务性：不足时回滚，提交后从干净快照确定性重放。

### 4. 建立安全状态投影

- 更新 Web 状态视图，并验证双方公开字段、本人私有字段和服务端内部字段的边界。
- 若桌面 TCP 也需要该值，同步更新 `network/protocol.py` 的发送与接收。
- 协议字段新增时优先提供兼容默认值；真正不兼容的更改必须提升协议版本。
- 前端类型只描述服务端实际返回的数据，不复制结算逻辑。

### 5. 注册显示名称和解释

当前 Web 前端统一在 `frontend/app/game-terms.ts` 注册解释，在
`frontend/app/game-client.tsx` 的状态展示映射中注册中文名称。每个新展示项至少包含：

- 简短名称；
- 一句话说明“它做什么”；
- 必要时补充触发/清除时机；
- 所属 UI 层级、排序和零值可见性；
- 对应的图标与色调，但不能只用颜色区分含义。

卡牌描述若出现这个术语，还应加入 `INLINE_RULE_TERMS`，让卡面文字也能复用同一份解释。
在后续状态种类增长后，应把这些元数据改为服务端下发的 `StatusDefinition` 目录，至少
包含 `id`、`label`、`description`、`category`、`visibility`、`order` 和
`hide_when_zero`；在完成该迁移前，不允许在多个组件里散落重复文案。

### 6. 按层级渲染，不为单个效果写整块页面

- 生命和能量使用专用组件。
- 次级属性与角色资源由通用列表消费显示元数据。
- 只有交互方式明显不同的状态（例如可点击生物、插入牌）才新增专用组件。
- 桌面与窄屏都必须允许资源换行，不能使用会吞掉状态的单行 `overflow: hidden`。

### 7. 完成四层验证

每个新效果至少覆盖：

1. **领域测试**：默认值、叠层、触发、递减/清除、胜负边界。
2. **协议测试**：公开值正确，本人私有值可见，对手和内部队列不泄露。
3. **前端契约测试**：术语解释、展示组件、可访问属性和兼容默认值存在。
4. **双浏览器流程**：创建/加入房间、选角、开局、触发效果，核对双方看到的值、
   tooltip、窄屏布局以及浏览器控制台。

最后运行：

```bash
python -m unittest discover -s tests
cd frontend
pnpm lint
pnpm test
pnpm build
```

## 完成定义

一个属性或效果只有在以下条件全部满足时才算完成：规则由服务端权威结算；状态放在
正确的类型化模型；公开/私有边界经过测试；界面层级、名称和解释已注册；鼠标和键盘
均可查看解释；桌面与移动布局不会隐藏它；测试、协议文档和变更日志已更新。
